## Исправлено

### P2 — рабочие настройки перезаписывались до завершения записи

`save_settings` сериализовал JSON и вызывал `fs::write` прямо для `settings.json`. Открытие существующего файла обрезало его до окончания записи. Сбой записи или остановка процесса между truncate и завершением могли оставить пустой/неполный JSON; существующий loader затем молча возвращал defaults. Терялись не только выбранные папка/Account/Server, но и локальные `forgottenAt`, `autostartSet`, `migratedAccounts`.

Формат и persistence вынесены из `gui.rs` в `settings.rs`. Сохранение полностью пишет `settings.json.tmp` в той же директории, вызывает `sync_all`, закрывает файл и только затем выполняет rename поверх рабочего JSON. Ошибка до замены не затрагивает рабочий файл. Reader читает только `settings.json`; незавершённый `.tmp` не становится настройками и перезаписывается следующей попыткой.

Это защита от частичной перезаписи одного файла, а не транзакция с Server или гарантия после потери питания: parent directory не fsync-ится. Требуется один writer; существующие вызовы после startup сериализуются model lock. Межпроцессная координация не добавлена.

### P2 — команды показывали успех и меняли активные настройки при ошибке сохранения

`detect_wow`, `set_wow_path`, `set_account`, `set_endpoint` сначала меняли Model и инвалидировали sync, затем игнорировали результат сохранения. Endpoint мог получить статус `ENDPOINT_SAVED`, хотя диск сохранял старое значение. Watcher/кеши/активная сессия уже переходили на новые настройки, а после рестарта возвращались прежние.

Теперь `Settings::update` редактирует копию, сохраняет её и только при успехе заменяет значение в памяти. GUI-операция `change_preferences` связывает это с инвалидацией поколения под тем же model lock. Затем вызывающая команда обновляет производное состояние, watcher или кеши. При ошибке ни один из этих последующих эффектов не выполняется, а команда возвращает ошибку через существующий локализованный `Shown`.

Forget намеренно не использует rollback предпочтений: после завершённого удалённого удаления модель остаётся revoked/forgotten даже при локальной ошибке, а сохранение/очистка повторяются прежним механизмом. Все существующие вызовы `save_settings`, включая Forget, используют новую файловую запись; обработка результата других lifecycle-вызовов этим не исправлена.

### Убрана лишняя запись

Импорт строки Plan переписывал settings, хотя менял только Plan и строку статуса. Этот вызов удалён. Импорт сохраняет прежний результат без ненужного дискового эффекта.

## Проверки и границы доказательства

Четыре новых headless Rust-теста используют реальные временные директории и production `Settings`:

- Ошибка staging write для четырёх видов предпочтений сохраняет прежние байты рабочего файла и настройки в памяти. После устранения причины повторное действие работает; lifecycle markers сохраняются.
- Отказ rename не применяет новое значение и не удаляет существующий destination. Повторная попытка после устранения причины проходит.
- Неполный оставшийся staging не читается как настройки; следующий save заменяет его.
- Прежний JSON без optional lifecycle-полей сохраняет defaults и читается после обновления без миграции формата.

Тесты сначала запускались на извлечённом адаптере прежнего поведения: прямой `fs::write`, замена памяти до сохранения и игнорирование ошибки. Три теста падали, один compatibility-тест проходил. После исправления проходят все четыре. Это red/green проверка сохранения и применения настроек, а не запуск полного GUI старого main. Отказ staging и rename вызывается реальной файловой системой; прерывание питания, заполнение диска посередине write и полный Tauri-сеанс не моделировались.

Локально проходят `pnpm test`: **979 Lua checks, 154 JS/contracts tests, 81 Rust tests**; также `pnpm lint`, `pnpm lint:companion:all`, `pnpm build`, `pnpm check-version`. ## Friction — что ещё поправить

- **Восстановление settings:** malformed/unreadable JSON по-прежнему превращается в defaults. TODO перенесён в `Settings::load`; нужно согласовать восстановление и сообщение игроку, а не молча придумать новое поведение. Этот PR предотвращает одну причину порчи, но не восстанавливает уже повреждённый файл.
- **Игнорируемые lifecycle saves:** `remember_migrations`, завершение reconnect, снятие forgotten marker при approved и initial autostart всё ещё могут обновить память без успешного сохранения. Для них нельзя механически применить rollback предпочтений: часть внешних действий уже произошла. Нужны явные результаты/повтор сохранения и отдельные регрессии.
- **Локальный Device:** `device.rs::write_file` всё ещё напрямую перезаписывает `device.json`; `read_file` сворачивает ошибки/невалидные данные в отсутствие credential. Windows может восстановить копию из Credential Manager, но это не общий протокол восстановления. Здесь не исправлено и не проверялось на отказах; требуются отдельные тесты сохранения и согласованная recovery policy.
- **F1, P1:** reconnect расходует старое право до надёжного сохранения нового credential. Потеря успешного ответа, ошибка записи или падение требуют согласованного протокола pairing; соответствующий TODO сохранён. Atomic settings не закрывает это окно.
- **F2, P1:** общий snapshot `savedAt` для Character/Account и отсутствие подтверждения каждой принятой Section остаются. Нужны контракт свежести/acknowledgements и решение владельца; TODO в `snapshot.rs` сохранён.
- **F4/F9, P2:** часть ошибок фоновых стадий скрывается, последовательные старые Requests могут задерживать готовый Plan. В этом проходе их поведение не менялось.
- Общий Prefetch budget, остальные secret-value collectors, advisory glib и модель единственного владельца остаются из предыдущих отчётов; новых проверок этих пунктов здесь не заявляется.
