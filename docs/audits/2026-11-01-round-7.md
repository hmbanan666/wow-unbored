База: `main` / `b3f52e6`, после слияния PR #46, 1 ноября 2026. Предыдущий отчёт: [шестой проход](2026-11-01-round-6.md).

В этом проходе проверены ручной fetch, фоновый Planner pass, порядок чтения acknowledgements, запись Plan/Advice/Suggestions, миграции, уведомления, итоговые ошибки и heartbeat. Это целевой аудит Companion; повторного полного аудита Server, addon collectors и зависимостей не заявляется.

## Исправлено

### P2 — поздний ответ мог заменить более свежий Prefetch внутри поколения

Защита из PR #46 отбрасывала результаты прежних settings/Device, но два прохода одного поколения оставались равноправными. Ручной fetch и background sync могли одновременно читать Server: более новый ответ записывался первым, после чего задержанный старый заменял Plan, Advice или Suggestions. Копии подтверждений отправки и результаты стадий также могли пересекаться. Mutex helper-файлов защищал отдельные операции записи, но не порядок чтения и применения целого прохода.

Теперь `Generation` владеет `Arc<Mutex<()>>`: та же идентичность служит проверке актуальности и содержит отдельную блокировку Prefetch. Она берётся до чтения входов и HTTP и удерживается до применения файлов, миграций, уведомлений и итогового статуса. В фоне heartbeat и error/status перенесены внутрь этого интервала; внешний loop больше не применяет итог Planner после освобождения блокировки. GitHub/addon preparation остаётся снаружи.

Оба входа проверяют поколение после ожидания. Старый queued fetch не продолжает чтение с устаревшими credentials. Forget/settings не берут Prefetch lock; инвалидация создаёт новое поколение с независимой блокировкой. Отдельно запущенный ручной fetch нового поколения не ждёт старую Prefetch-блокировку. Старый blocking HTTP при этом не отменяется, единственный background loop ждёт его возврата, а progress сохраняет собственную общую блокировку.

Model lock по-прежнему удерживается только для локальных действий, а не на время HTTP. Порядок Prefetch → progress → model согласован с watcher/manual progress; ни один из них не пытается взять Prefetch, удерживая progress или model. FIFO для ожидающих вызовов не обещается: важен последовательный интервал от чтения до применения, а не порядок кликов.

### P1 — первая реализация могла заблокировать GUI при ожидании Prefetch

Независимое Spec review обнаружило проблему до публикации PR: синхронная Tauri-команда `fetch_plan` ждала Prefetch lock на GUI-потоке. Background, удерживая этот lock, при изменении pairing вызывает `refresh_view`; `tray.set_tooltip` передаёт работу GUI-потоку и ждёт её завершения. Возникало циклическое ожидание. Даже без него ожидающий fetch мешал обработке команд окна.

Это подтверждено установленными исходниками Tauri 2.12.5 (`tray/mod.rs`, `menu/mod.rs`, command wrapper) и [официальной документацией команд](https://v2.tauri.app/develop/calling-rust/). Исправлено: команда стала async, захватывает session до постановки работы, затем ожидает `spawn_blocking`. Вся блокирующая часть, включая ожидание mutex и reqwest, выполняется в blocking worker. Ошибка worker использует существующий локализованный `ERR_UNEXPECTED`; новых UI-строк нет.

## Проверки и границы доказательства

Добавлены три headless Rust-теста в `sync_state.rs`:

- Два пересекающихся Prefetch одного поколения: первый удерживает задержанный ответ, второй ждёт перед чтением acknowledgements. После обоих проходов реальные Plan/Advice/Suggestions и status содержат новое значение; подтверждения и уведомления идут в порядке применения. Тест использует общий Plan fixture и реальные функции записи файлов.
- Ожидающий проход старого поколения после инвалидации не применяется; отдельно запущенное новое поколение получает свою блокировку, пока старая ещё удерживается. Model остаётся доступной для инвалидации.
- Ошибка прохода освобождает guard, следующий проход может начаться.

До реализации блокировки первый тест запускался с no-op входом, моделирующим прежнюю конкурентность: падение `a second fetch started before the first applied: Ok([])`. После реализации проходят все семь тестов `sync_state`, включая четыре прежние регрессии Forget. Это red/green проверка механизма с адаптером старого поведения, а не запуск неизменённого main с методом, которого там ещё не было.

Тесты моделируют задержку ответа через channels и вызывают реальные helper writers; они не поднимают Server и не исполняют Tauri GUI. В частности, headless-тест не обнаруживал GUI deadlock — его нашло ревью. Исправленный dispatch проверен чтением вызовов, компиляцией и clippy всех features/targets. Ручные сценарии задержанного pairing, двух fetch и Forget/reconnect добавлены в `TESTING.md`; live WoW и полный Tauri-сеанс не запускались.

На основном исправлении прошли `pnpm test` (**979 Lua checks, 154 JS/contracts tests, 77 Rust tests**), `pnpm lint`, `pnpm lint:companion:all`, `pnpm build`, `pnpm check-version`. После правки async dispatch повторены 77 Rust tests, all-targets/all-features GUI clippy и cargo fmt; изменялись Rust и документация. Windows installer проверяется CI.

## Friction — что остаётся

- **F1, P1:** восстановление reconnect после потери успешного ответа или ошибки сохранения credential требует согласованного протокола pairing. TODO в `gui.rs` сохранён. Потеря ответа Forget/падение до durable marker также не решаются mutex в памяти.
- **F2, P1:** Character и Account имеют разные времена сохранения, но общий snapshot `savedAt`; HTTP success не подтверждает принятие каждой Section. TODO в `snapshot.rs` сохранён. Нужны контракт и решение владельца с учётом Wins/перемещения предметов.
- **F4/F9, P2:** ошибки некоторых стадий по-прежнему отбрасываются; последовательные Requests с таймаутами задерживают Plan. Сериализация делает второй fetch ожидающим первого; она не сокращает сетевой проход и не отменяет запросы. Нужна отдельная работа над результатами стадий и диагностикой, без выдумывания новых уведомлений игроку.
- **Хранение settings:** прямая запись JSON, fallback к default при повреждении и игнорирование ошибок частью setters остаются. Нужна согласованная обработка надёжности сохранения и восстановления.
- Mutex действует в одном процессе. Ручной импорт строки Plan, updater и отдельные progress-команды не становятся одной транзакцией с Prefetch. Общий размер helper-файлов по-прежнему рассчитывается при записи Advice относительно уже лежащих файлов; этот проход не доказывает соблюдение budget при любом последующем росте Plan.
- Остальные collectors, advisory по glib и модель единственного владельца здесь повторно не проверялись. Их пункты из предыдущих отчётов не закрыты.
