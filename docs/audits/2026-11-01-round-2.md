# Аудит после слияния PR #35 и #36

База: `main` / `92b50e0`, 1 ноября 2026. Продолжение [первого аудита](2026-11-01.md). Проверены принятие snapshot и legacy profile, производные поля Character, выбор ожидаемого Request, обработка HTTP-отказов, подтверждение миграции Account и формирование `Plan.lua`.

Это целевой проход по сохранности данных и доставке Requests, а не утверждение о полном отсутствии дефектов во всём репозитории. Изменений wire contract, зависимостей и новых продуктовых решений нет.

## Исправлено

### 1. P2 — поздняя выгрузка откатывала каталог Character

**Где:** [DataStore](../../apps/server/src/data.ts), `touchCharacter` и `putSection`. Закрывает F5 первого аудита.

При поступлении `Mage / 80`, а затем старого `Warrior / 70`, тело Section правильно оставалось свежим, но каталог уже содержал старые класс и уровень. Старый upload также мог заменить связь Account/Device и сведения о пропущенных Sections.

Теперь контакт обновляет `last_seen` независимо от свежести. Метаданные выгрузки не откатываются по старому `savedAt`, а класс и уровень вычисляются из принятой `char` Section после проверки её собственной свежести. Это не общий запрет принимать поздние snapshots: отдельная Section может оказаться новее сохранённой, даже если другая Section уже имеет более позднюю дату.

HTTP-регрессии проверяют и сохранённое тело, и каталог. В сценарии `char@100 → bags@400 → char@300 → char@200` каталог принимает `char@300` и отвергает откат от `char@200`. Простая проверка общего времени Character потеряла бы правильное обновление.

### 2. P2 — legacy profile затирал сведения из новых Sections

**Где:** [DataStore](../../apps/server/src/data.ts), `ingestProfile` и `refreshCharacterFacts`.

Даже более поздняя отправка старого profile могла заменить уровень и класс каталога устаревшим контекстом, хотя `profileView` уже отдавал приоритет `char`. Теперь каталог следует тому же правилу: profile служит источником только при отсутствии `char`.

Производные поля обновляются в общей границе принятия Section, поэтому правило действует для snapshot, profile и backfill. Неизменная повторная отправка также исправляет ранее испорченный индекс без новой записи истории. Отсутствующий уровень и пустой класс не стирают известные значения. Это не массовая миграция старых индексов: до следующего принятого или неизменного upload старые ошибочные строки могут оставаться.

### 3. P2 — отказ старого Request подменял новый

**Где:** [request.rs](../../apps/companion/src-tauri/src/request.rs), [gui.rs](../../apps/companion/src-tauri/src/gui.rs), `post_requests` и `sync_plans`. Закрывает F3 первого аудита.

`rejected.first()` обходил выбор ожидаемого Request. Отклонённый Request другого Character мог постоянно занимать `Plan.lua`, даже если более новый Request был принят. Новый тест воспроизвёл это в обоих порядках обхода.

Ожидаемый Request выбирается из всей пачки до отправки. Только его постоянный отказ может записать failure. При отказе обоим Requests файл содержит id нового и Reason code `rejected`. Отказ теперь проходит через существующий `pick_plan_file` и общий путь обновления `request_pending`; дублирующий ранний выход удалён.

Обработка пачки вынесена из GUI в модуль Request с подменяемой отправкой. Это позволяет проверять порядок, HTTP-отказы и подтверждение миграции Account без Tauri. GUI читает файлы и выполняет HTTP-запросы; отдельной системы retries или новых интерфейсных состояний не добавлено.

### 4. P2 — временные HTTP 408/429 превращались в окончательный отказ

**Где:** [request.rs](../../apps/companion/src-tauri/src/request.rs), классификация результата отправки.

Раньше любой 4xx, кроме 401, давал `failed/rejected`. Теперь 408 и 429, как 401 и 5xx, завершают текущий проход ошибкой и используют существующий повтор sync. Они не записывают терминальный отказ в `Plan.lua` и не подтверждают миграцию Account.

Тест перебирает 401/408/429/500/503, проверяет сохранение миграции для повторной отправки и её подтверждение после HTTP 200. Дополнительно проверено, что ошибка проходит существующую локализацию Companion, а не превращается в неизвестную строку. Серверный ответ с произвольным текстом ошибки больше не разбирается ради неиспользуемого значения.

## Friction — что осталось

### F1. P1 — восстановление Connect again после потери ответа или записи

Из первого аудита: Server расходует право reconnect раньше, чем Companion надёжно сохраняет новые credentials. Нужны согласованные с владельцем семантика повторной операции и ADR по pairing. Существующий `TODO(audit)` оставлен. Технический аудит не выбирает за владельца новое правило восстановления доступа.

### F2. P1 — один savedAt для разных Character/Account файлов

Из первого аудита: свежие Account Sections могут получить время старого Character и быть отвергнуты; успешный HTTP-статус ещё не означает принятия каждой Section. Исправление каталога не решает этот дефект. Нужны согласованный контракт свежести и общая fixture. Простое разбиение upload затрагивает сопоставление перемещений предметов и Wins. Существующий `TODO(audit)` оставлен.

### F4. P2 — ошибки фоновых этапов sync остаются потерянными

В `sync_plans` по-прежнему отбрасываются результаты snapshot, profile, Suggestions и Advice. Plans должны оставаться независимыми от этих ошибок, но потеря результата скрывает неполную синхронизацию. Следующая техническая граница: явные результаты этапов и диагностические записи без персональных данных; правило уведомления игрока следует отдельно согласовать.

### F9. P2 — временный отказ старого Request задерживает актуальный

Оставшаяся связь подтверждена чтением `post_requests` и `sync_plans`, также отмечена обоими ревью: `send(...)?` или временный HTTP-статус прерывает всю пачку, затем не выполняется чтение актуального Plan. Исправление постоянных отказов это не устраняет. Управляемый тест всей sync-петли пока отсутствует.

Следующий PR должен разделить результаты отдельных отправок и получение актуального Plan, сохранив честную диагностику и подтверждение миграции только успешными ответами. Сортировка Requests или молчаливое игнорирование ошибок не устранят причину. Пауза до следующего прохода остаётся общей; поддержки Retry-After эти изменения не добавляют.
