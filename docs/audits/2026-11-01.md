# Аудит Unbored — 1 ноября 2026

База: свежий `main`, `4ae9f7d`. Рабочее дерево перед аудитом было чистым. Аудит охватывает границы доверия и сохранения данных в аддоне, Companion, Server, общие контракты, проверки и выпуск. Это проверка кода с воспроизведением конкретных ошибок, не сертификация всех путей WoW API и не проверка работающего production Server.

Основной вывод: у проекта уже есть полезные ADR, общие fixtures и быстрые проверки, но тесты лучше покрывают отдельные успешные операции, чем пересечение операций: повтор, замена, закрытие во время чтения, удаление во время ожидания. На исходном `main` весь `pnpm test` и `pnpm lint` проходил, несмотря на перечисленные ниже ошибки.

Исправления разделены на два независимых PR от одной базы: `fix/server-device-isolation` и `fix/snapshot-integrity`. В них нет массовой косметической переработки, новых игровых возможностей или изменения формата payload. Изменения реализуют существующие ADR. Новые решения о pairing, приватности и контракте остаются в Friction.

## Исправлено

### 1. P1 — чужой Request возвращался при повторе его id

**Где:** [Store.addRequest](../../apps/server/src/store.ts), `POST /v1/requests`.

**Сценарий:** Device A создаёт Request. Одобренный Device B отправляет тот же id. Дедупликация возвращала существующий Request со статусом 200 без проверки `deviceId`, хотя GET того же Request для B правильно возвращал 404. В ответ попадали данные A.

**Исправление:** идемпотентность ограничена создавшим Request Device; чужое совпадение отклоняется общей ошибкой 400 без содержимого Request. Регрессионный HTTP-тест проверяет обе стороны: собственный повтор допустим, чужой — нет.

### 2. P1 — Request Plans попадали в общий «последний Plan», а замены переживали удаление

**Где:** [latestPlan / fulfillRequest / deleteRequests](../../apps/server/src/store.ts), [GET /v1/plan](../../apps/server/src/app.ts).

**Сценарий:** последний Plan для Request A выдавался Device B через общий endpoint. Дополнительно после замены `requests.plan_id` старый Plan терял текущую связь с Request; Forget удалял только последнюю версию.

**Исправление:** `plans.request_id` сохраняет происхождение Plan. Выбор для Companion учитывает Device. Удаляются все Plans этого Request, включая замены. Одноразовая транзакционная миграция восстанавливает связи из Requests и Player history. Проверены миграция, повторное открытие БД, замена и удаление.

Явные direct Plans без Request сохраняют существующее общее поведение. Это отдельная граница продукта, а не доказательство изоляции всех Accounts. Происхождение, уже утраченное вместе с Request и его history до миграции, восстановить достоверно нельзя.

### 3. P1 — поздний Plan мог появиться после Forget my data

**Где:** [HTTP put Plan](../../apps/server/src/app.ts), [MCP put_plan / answer_request](../../apps/server/src/mcp.ts), [Store.putPlan](../../apps/server/src/store.ts).

**Сценарий:** проверка существования Request проходила, затем обработчик ожидал Blizzard API. В этот момент Forget удалял Request. После ожидания вставлялся Plan без связи; попытка выполнить уже удалённый Request ничего не делала. Plan оставался доступен как direct.

**Исправление:** проверка Request и запись его происхождения выполняются на синхронной границе вставки Plan после внешнего ожидания. Тест подставляет асинхронный Blizzard fetch, выполняет Forget внутри ожидания и проверяет отсутствие любого сохранённого Plan. Все три входа воспроизведены отдельно.

### 4. P2 — повтор Forget отключал Connect again

**Где:** [Store.forgetDevice](../../apps/server/src/store.ts).

**Сценарий:** первая операция удаляла данные и разрешала повторное подключение. Повтор после потери ответа видел уже revoked Device и сбрасывал это разрешение.

**Исправление:** повтор сохраняет право, выданное предыдущим Forget. Владелец по-прежнему может отозвать Device; owner revoke и никогда не одобренный Device не получают обход проверки. HTTP-тест повторяет Forget перед Connect again.

### 5. P2 — новая версия Section терялась при неизменном теле

**Где:** [Companion snapshot](../../apps/companion/src-tauri/src/snapshot.rs), [DataStore.putSection](../../apps/server/src/data.ts).

**Сценарий:** `v` меняется, canonical body остаётся тем же. Companion считал Section уже отправленной; Server также сравнивал только hash и не сохранял новую версию.

**Исправление:** внутренняя квитанция Companion — типизированная пара версии и hash. Server сравнивает обе части. Wire hash по-прежнему считается только по телу, fixtures и формат не меняются. Смена версии записывается как full history, повтор не создаёт новую запись; неизвестная новая версия не выдаётся за известную старую. Есть Rust- и HTTP-регрессии.

### 6. P2 — неизменная свежая выгрузка не защищала от старой изменённой

**Где:** [DataStore.putSection](../../apps/server/src/data.ts).

**Сценарий:** принято тело A со временем 100, затем A со временем 300. Второй upload считался unchanged и оставлял время 100. Позднее тело B со временем 200 принималось поверх более свежего состояния.

**Исправление:** unchanged обновляет максимальное принятое `savedAt`, не добавляя history. Проверка устаревания выполняется раньше дедупликации. HTTP-тест проверяет сохранность A и отсутствие ложного изменения истории. Это исправление не решает неодинаковые времена Character/Account файлов: см. F2.

### 7. P2 — поэтапное чтение продолжалось после закрытия банка

**Где:** [Snapshot worker](../../addon/Core/Data/Store.lua).

**Сценарий:** collector проверял открытое окно только при запуске. После `Yield` окно могло закрыться, а coroutine продолжала читать и публиковала смешанный или неполный результат.

**Исправление:** worker проверяет открытое окно и номер его закрытия перед каждым возобновлением. Закрытие и повторное открытие между кадрами тоже отменяют старое чтение. Последняя завершённая Section сохраняется, новое открытие допускает новый проход. Lua-тест проверяет отсутствие дальнейших чтений и частичной записи.

### 8. P2 — ACHIEVEMENT_EARNED читал API в бою

**Где:** [Collections](../../addon/Core/Data/Collections.lua), [Snapshot worker](../../addon/Core/Data/Store.lua).

**Сценарий:** delta немедленно вызывала `GetTotalAchievementPoints`, обходя запрет чтения в бою и очередь settled events.

**Исправление:** id сохраняется из полезной нагрузки события; чтение очков выполняется через отложенный worker вне боя. При свежем полном снимке не повторяется весь проход достижений. Если суточный проход уже нужен, queued event не может его вытеснить. Обе ситуации покрыты Lua-регрессиями; второй случай найден независимым ревью и исправлен до публикации.

## Friction — осталось решить

Пункты ниже не следует считать исправленными этими PR. Указано, где есть прямое следствие кода, а где ещё нужна проверка с управляемыми сбоями. `TODO(audit)` добавлены около reconnect, выбора rejected Request и общего времени snapshot.

### F1. P1 — Connect again не восстанавливается после потери ответа или записи на диск

[gui.rs: connect_again](../../apps/companion/src-tauri/src/gui.rs) сначала вызывает Server, который расходует право старого Device на reconnect, и только потом сохраняет новые credentials. Потеря успешного ответа или ошибка записи оставляет PC со старым secret, повтор которого Server уже отвергает. Порядок операций подтверждён кодом; сбой реальной Tauri-команды в этом аудите не инжектировался.

Нужен отдельный PR после решения с владельцем по ADR 0045: восстанавливаемая операция с заранее надёжно записанным намерением и безопасным повтором на Server. Просто повторить HTTP-запрос или поменять местами две строки недостаточно. Тесты должны остановить процесс до отправки, после принятия Server и до/после локального сохранения.

### F2. P1 — у Account Section может оказаться время другого, давно не игравшего Character

[snapshot.rs: build_upload](../../apps/companion/src-tauri/src/snapshot.rs) объединяет два файла, но выбирает один `savedAt`, отдавая приоритет Character. [gui.rs: post_snapshots](../../apps/companion/src-tauri/src/gui.rs) перебирает всех Characters. Свежие Account Sections могут уйти вместе со старым Character-файлом, получить его время и быть отвергнуты как stale. Companion запоминает отправленную ревизию по успешному HTTP-статусу даже при `stale` в JSON. Это подтверждается порядком сборки и подтверждения данных в коде; end-to-end тест с двумя файлами ещё нужен.

Нужен согласованный контракт свежести по scope/Section, общая fixture и тест на всех трёх сторонах. Простое разбиение на два HTTP upload опасно: обнаружение переносов предметов и Wins сравнивает несколько Sections одной выгрузки. Это решение о данных по правилам AGENTS.md требует обсуждения и ADR.

### F3. P2 — отказ старого Request перекрывает новый ожидаемый

[gui.rs: sync_plans](../../apps/companion/src-tauri/src/gui.rs) выбирает `rejected.first()` до запроса статуса `waiting`. `post_requests` собирает Requests всех Characters. Поэтому старый отклонённый Request другого Character может постоянно заменять актуальный Plan.lua. Причина видна в коде; воспроизведение через весь sync worker ещё отсутствует.

Следующее исправление: выбор по waited Request, общий механизм выбора статуса для успешного и отклонённого ответа, тест с двумя Character-файлами в обоих порядках обхода.

### F4. P2 — ошибки фоновой отправки данных теряются

[gui.rs: sync_plans](../../apps/companion/src-tauri/src/gui.rs) отбрасывает ошибки snapshot, legacy profile, Suggestions и Advice через `let _ = ...`. Независимость Plans от фоновых ошибок полезна, но сейчас она достигается потерей результата: соединение может выглядеть рабочим, пока данные не доходят.

Нужен результат каждого этапа sync, ограниченный повтор и диагностическая запись без персональных данных. Отдельно согласовать, когда показывать игроку уже имеющуюся локализованную строку: каждую временную сетевую ошибку показывать не стоит. Проверять отказ каждого этапа при продолжающейся доставке Plan.

### F5. P2 — stale snapshot всё ещё может откатить метаданные Character

[DataStore.touchCharacter](../../apps/server/src/data.ts) обновляет `class`, `level`, `account_id`, `device_id` до того, как `putSection` отбрасывает старое тело. `saved_at` берёт MAX, а уровень — просто пришедшее значение. Поэтому метаданные каталога могут противоречить сохранённой свежей char Section. Это отдельный оставшийся дефект по коду; новый тест watermark проверяет Section, а не этот индекс.

Следующее исправление: обновлять производные метаданные из принятой char Section и отдельно учитывать факт контакта Device. Нужен HTTP-тест «level 80 → поздний level 70»: и Section, и каталог остаются на 80.

### F6. P2 — модель secret values в тестах слишком слабая

`addon/tests/data.lua` подставляет обычную Lua-таблицу как SECRET. Это проверяет удаление значения перед записью, но не все ограничения настоящих WoW secret values. В collectors остаются обращения и сравнения до очистки: например, флаги достижений в Collections и календарные даты/ключи в World.

Это пробел доказательств, не утверждение о воспроизведённом падении live-клиента. Следующий проход должен проверять guards до сравнения, арифметики и индексации, а не только `S.Clean` на готовом результате. Для фактических ограничений 12.x нужен клиент и существующий TESTING.md. Аналогично остаются явные `TODO(verify-in-game)` для фильтров коллекций, /played и API профессий/репутаций.

### F7. P3 для нынешней Windows-поставки — открытый advisory glib

GitHub Dependabot alert 5 открыт для `glib 0.18.5` из Cargo.lock. [GHSA-wrw7-89jp-8q8g](https://github.com/advisories/GHSA-wrw7-89jp-8q8g) описывает unsound iterator; исправленная ветка начинается с 0.20.0. `cargo tree --locked --target x86_64-pc-windows-msvc -i glib` не показывает зависимость; Linux target показывает путь через GTK/Tauri.

Это не подтверждённая уязвимость выпускаемого Windows installer. Нужно отдельно отслеживать обновление совместимой GTK/Tauri-цепочки и целевые платформы. Принудительно подменять major-версию transitive crate в lockfile без совместимой цепочки нельзя. Alert не закрывался и зависимости в этом аудите не менялись.

### F8. Перед несколькими независимыми владельцами — определить владение Account и direct Plans

В коде ещё есть наследие одного владельца: `PLAYER = "self"`, идентичность Character по name/realm, общий direct Plan, принятие Account из upload и миграция `accountLegacy`. Новый PR закрывает конкретные утечки Request/Plan, но не превращает Server в систему с полной изоляцией разных владельцев.

До публичного запуска нужны ADR о доказательстве владения Account, связи нескольких PCs, миграции и назначении direct Plan. Нельзя молча придумать это при техническом аудите. При текущей модели одного владельца это граница применимости, а не автоматически критический публичный инцидент.

## Где улучшать структуру кода

- **Companion:** вынести sync из `gui.rs` в тестируемый модуль с явными операциями отправки, подтверждения, выбора актуального Request и записи helper-файлов. Tauri-команды должны управлять состоянием и отображением. Критерий пользы — возможность воспроизвести F1–F4 без запуска GUI, а не уменьшение числа строк файла.
- **Server:** сосредоточить Request, его Plans и их удаление в одной границе записи; derived metadata обновлять из принятого snapshot. Не переносить одинаковые проверки доступа по каждому endpoint. PR #35 уже усиливает такую границу для Plan insertion.
- **Addon:** сохранить один worker и общий жизненный цикл чтения. Отдельно инвентаризировать callbacks `onEvent`/`delta`, которые обходят `S.Read`; исправление achievements показывает, почему одного guard в `S.Read` недостаточно.
- **Проверки:** расширять не happy-path fixtures, а сценарии «повтор + частичный успех», «старое после нового», «удаление во время await», «закрытие между кадрами». Форматирование и размеры файлов сами по себе не являются дефектами архитектуры.

Документированных нарушений и полезных новых замечаний о структуре кода: **0**. Дополнительно обнаружена одна оставшаяся ошибка корректности — удаление Request во время проверки Plan. Она совпала с находкой Spec и закрыта регрессионными тестами трёх входов.

### Изоляция — Spec

На исходном diff: **1 замечание, P1** — поздний Plan после Forget нарушает ADR 0002/0043. После ревью проверка перенесена в Store.putPlan. Остальные проверки владения, замены, миграции, удаления и повтора Forget соответствуют ADR; расширения продуктового поведения не найдено.

### Данные — Standards

**0 замечаний.** Версия и hash представлены одним типом; wire contract сохранён; изменения жизненного цикла чтения соответствуют ADR. Ревью отдельно подтвердило, что F2 не решён и нельзя заявлять исправление всей свежести snapshots.

### Данные — Spec

Остальные изменения соответствуют требованиям. Новое независимое ревью после этих двух точечных исправлений не запускалось; выполнены регрессионные проверки.
