# Четвёртый проход аудита

База: `main` / `e7487ea`, после слияния PR #39–41, 1 ноября 2026. Предыдущий отчёт: [третий проход](2026-11-01-round-3.md).

Проверены авторизация upload после асинхронного чтения тела, гонка с Forget/owner revoke, обработка частично успешной пачки Requests и подтверждение миграции Account. Дополнительно просмотрен локальный путь Forget в Companion. Контракты, зависимости, интерфейсные строки и правила pairing не менялись.

## Исправлено

### 1. P1 — уже начатый upload восстанавливал данные после Forget

**Где:** [app.ts](../../apps/server/src/app.ts), POST `/v1/snapshot`, `/v1/profile`, `/v1/requests`, `/v1/progress`.

Маршрут проверял Device, затем выполнял `await` чтения тела и сохранял данные по старому разрешению. Пока тело приходило, другой HTTP-запрос успевал выполнить Forget или владелец отзывал Device. Исходный upload всё равно отвечал 200/201 и мог снова записать удалённые данные. Это нарушало ADR 0043: после отзыва больше ничего не сохраняется от этого Device.

Добавлены восемь HTTP-регрессий: четыре маршрута × два способа отзыва. Тест передаёт настоящий `ReadableStream` с `highWaterMark: 0`, дожидается чтения после первоначальной авторизации, выполняет Forget/revoke и только затем отдаёт тело. Snapshot передаётся с gzip. На исходном коде все восемь тестов получали 200/201 вместо 401.

Теперь общая `allowCompanion` вызывается до чтения тела и повторно непосредственно перед синхронными изменениями, включая `bindAccount`. Между окончательной проверкой и этими записями нет нового `await`. Ранний отказ до чтения тела сохранён; shared token и обычные одобренные Devices используют прежние правила.

После исправления каждый отозванный upload получает 401. Тесты также сравнивают количество строк в Accounts, Characters, Sections и их истории, profiles, Requests, Plans, progress, history и Suggestions до/после освобождения тела. Это проверяет отсутствие побочных записей, а не только HTTP-ответ.

Авторизация не размножена по новым реализациям: все проверки используют существующую функцию. Явное расположение проверки у записи оставлено намеренно. Если в будущем между ней и записью появится `await`, разрешение потребуется проверить заново.

### 2. P2 — временный отказ старого Request останавливал обработку актуального

**Где:** [request.rs](../../apps/companion/src-tauri/src/request.rs), `post_requests`; [gui.rs](../../apps/companion/src-tauri/src/gui.rs), `sync_plans`. Закрывает путь прерывания пачки из F9 предыдущего отчёта.

После прошлого исправления постоянный отказ старого Request уже не подменял новый, но transport error, 408/429, 401 или 5xx по старому Request всё ещё завершали всю пачку ошибкой. В результате актуальный Request мог не отправиться, либо обработка не доходила до чтения его Plan. Новый тест воспроизвёл прерывание на транспортной ошибке.

Теперь для более ранних Requests возвращается список отложенных ошибок: только `Transport` или `Http(status)`. Пачка продолжает обрабатывать ожидаемый Request. GUI пишет эту безопасную диагностику в stderr; нет Request id, Account, тела или произвольного текста сетевой ошибки. Это диагностический вывод, не новый постоянный журнал и не уведомление игроку.

Ожидаемый Request выбирается по прежнему D82. Его собственная временная ошибка по-прежнему возвращается в обычный путь ошибки Companion; его постоянный отказ даёт прежний Reason code. Отложенный старый Request остаётся в SavedVariables и повторяется на следующем проходе. Новая очередь, отдельные timers или новый способ retry не вводились.

Тесты проверяют оба порядка Characters и transport/401/408/429/503, постоянный отказ именно ожидаемого Request и сохранение его транспортной ошибки. Разные Accounts подтверждают, что успешная отправка подтверждает только свою миграцию: у неудачной `accountLegacy` остаётся для повтора и исчезает после последующего успеха.

## Что стало лучше в структуре

- Проверка права записи видна у каждой синхронной операции Server и использует одну реализацию авторизации. Не добавлен общий middleware, который скрывал бы место возможного `await`.
- Модуль Request возвращает различимые результаты частичного успеха. GUI отвечает за техническую диагностику, а не переопределяет, какой Request важнее.
- У транспортных диагностик ограниченный тип, поэтому нельзя случайно вывести произвольный сетевой текст или данные игрока через этот путь.
- Регрессии воспроизводят порядок событий без sleeps: поток запроса удерживается явно, а отправка Requests подменяется через существующий адаптер.

## Friction — что остаётся

### Локальная запись после Forget не отменена этим исправлением Server

Companion может получить Advice, Suggestions или Plan до Forget, дождаться завершения очистки и затем записать уже полученный результат. Блокировка helper-файлов из прошлого PR защищает одну файловую операцию, но не валидность старого сетевого результата. Старый ответ о pairing также может обновить модель GUI.

В коде `sync_planner` всё ещё есть повторная очистка для revoked/forgotten Device; это ограничивает последствие, но не устраняет гонку. Нужен общий механизм поколения синхронизации: захват поколения вместе с настройками/Device и проверка непосредственно при применении файлов, caches и GUI-state; Forget и reconnect должны инвалидировать старое поколение. Простая проверка флага до HTTP или ещё один `clear_helper` после задержки оставит окно гонки. В этом проходе сценарий подтверждён порядком вызовов, а не управляемым Tauri-тестом.

### F9 — прерывание исправлено, задержки и ошибка текущего Request остались

Отправка остаётся последовательной. Несколько старых сетевых таймаутов способны задержать весь проход, хотя больше не прерывают его. Ошибка upload самого ожидаемого Request всё ещё останавливает последующее получение Plan, даже если Server уже успел его принять. Полная независимость чтения готового Plan от отправки Requests не заявляется.

### F1/F2 — решения по восстановлению и свежести всё ещё нужны

- **F1, P1:** reconnect расходует право старого Device до надёжного сохранения нового credential. Нужны согласованные семантика повторной операции и ADR по pairing; существующий TODO оставлен.
- **F2, P1:** Character и Account файлы объединяются с одним `savedAt`, а успешный HTTP сам по себе не доказывает принятия каждой Section. Нужны согласованный контракт и fixtures с учётом Wins/перемещений предметов; существующий TODO оставлен.

### Остальные границы

- **F4:** результаты snapshot/profile/Suggestions/Advice по-прежнему отбрасываются. Новая диагностика касается только старых Requests и не решает наблюдаемость всей sync-петли.
- Общий Prefetch budget после последовательной записи всех файлов, межпроцессная координация и ограничения остальных collectors на secret values не получили новых исправлений.
- В snapshot route фактическая длина проверяется после `arrayBuffer()`: лимит размера данных не является ограничением памяти во время чтения потока без достоверного Content-Length. Это статический риск границы приёма; нагрузочное воспроизведение и исправление ограниченного чтения не выполнялись.
- Модель одного владельца, владение Account и dependency advisory из первого отчёта не пересматривались. Live WoW, Windows installer и production Forget не запускались.
