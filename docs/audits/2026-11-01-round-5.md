# Пятый проход аудита

База: `main` / `36e0584`, после слияния PR #42–43, 1 ноября 2026. Предыдущий отчёт: [четвёртый проход](2026-11-01-round-4.md).

Этот проход проверяет границу приёма Game data snapshot и достоверность `achProgress`: потоковое чтение, размер буфера, ошибки транспорта, сохранение авторизации после Forget, а также неизвестные/secret флаги достижений и критериев. Дополнительно повторно просмотрены незакрытые пути Companion: Forget, reconnect, свежесть snapshot и последовательная отправка Requests. Это направленный аудит этих областей, не утверждение об отсутствии дефектов во всём репозитории.

## Исправлено

### 1. P2 — лимит snapshot срабатывал после чтения всего тела

**Где:** `apps/server/src/app.ts`, POST `/v1/snapshot`.

Маршрут проверял заявленный Content-Length, затем вызывал `arrayBuffer()` и сравнивал фактическую длину с 4 МБ. При chunked-загрузке или недостоверном заголовке приложение сначала накапливало всё тело. Лимит ADR 0029 ограничивал сохранённые данные, но не накопление при чтении. Реальная нехватка памяти или падение production не воспроизводились; подтверждено избыточное потребление потока.

На исходном коде тестовый поток отдавал все четыре чанка, хотя уже второй превышал лимит. Два случая — без Content-Length и со значением `1` — одинаково воспроизводили дефект. Дополнительный тест через настоящий `@hono/node-server` отправляет chunked HTTP по localhost, превышает лимит и намеренно не вызывает `request.end()`: исходный обработчик не отвечал и достигал тестового таймаута.

Теперь `snapshotBytes` проверяет фактическую длину каждого чанка до копирования. При превышении reader отменяется, возвращается 413. Ошибка или незавершённая очистка producer не блокирует ответ. Буфер растёт по мере чтения до установленного cap; нет массива объектов на каждый маленький чанк. Наружу возвращается только записанная часть буфера.

Это ограничение аккумулятора приложения, а не всей памяти соединения: текущий входной чанк, временная копия при росте, распаковка, JSON, HTTP-адаптер и proxy имеют свои расходы. Управление socket cleanup остаётся у адаптера. HTTP-регрессия подтверждает ранний ответ до EOF, но не отсутствие абсолютно всех последующих чтений сокета.

Сохранены ранняя авторизация, ранний отказ по заведомо большому Content-Length, допустимый размер ровно 4 МБ, gzip, отдельный предел распаковки 32 МБ и повторная проверка Device непосредственно перед синхронными записями. Между окончательной проверкой и записью не появился `await`.

### 2. P2 — обрыв snapshot попадал в общий 500

Чтение тела находилось вне блока обработки malformed JSON/gzip. Ошибка stream уходила в общий обработчик Hono: 500 и сырой текст исключения в stderr. Тест воспроизвёл это с искусственной транспортной ошибкой; реальные персональные данные в логах не исследовались.

Теперь чтение входит в тот же защищённый блок, что и декодирование. Ошибочное тело даёт существующий нейтральный ответ 400; частичный snapshot не записывается. Отдельная регрессия проверяет статус, текст ответа и отсутствие Accounts. Обе проблемы исправлены одним PR Server, поскольку относятся к одной границе чтения тела.

### 3. P2 — неизвестный флаг превращался в ложный прогресс достижения

**Где:** `addon/Core/Data/Collections.lua`, `achProgress`.

Проверки `completed ~= true` и `isGuild ~= true` пропускали nil, secret и неверные типы как незавершённое личное достижение. В критериях неизвестный `done` считался открытым; для progress bar читались quantity/required без подтверждения доступного флага. Так в Section появлялись строки, не доказанные игровыми данными, вопреки ADR 0027 и D182.

Добавлен небольшой `AsBoolean`: читабельные true/false остаются boolean, неизвестное становится nil. Он проверяет `issecretvalue` до сравнения; ошибка самого secret check тоже даёт nil. Существующий `Flag`, где вызывающие места ожидают false по умолчанию, не изменён.

`achProgress` теперь требует явно false для completion и guild, а для каждого посчитанного критерия — известный done. Неизвестный критерий исключает строку всего достижения: из неполных данных нельзя достоверно получить отношение прогресса. При следующем доступном чтении обычная строка снова формируется. Расписание, пороги, сортировка, количество строк, лимиты вызовов и форма Section не менялись.

На исходном collector падали 16 новых проверок: secret/неверный тип/nil в четырёх местах. Финальные 20 новых проверок дополнительно покрывают обычный false, отказ secret check, boolean-shaped secret и восстановление доступного progress bar. Это Lua-модель игрового API; реальные Midnight secrets требуют проверки в WoW.

## Friction — что остаётся

- **P1, локальное применение после Forget:** `fetch_plan`/`sync_planner` работают с копиями settings/Device; старый ответ может записать Plan/Advice/Suggestions или обновить pairing после локальной очистки. Повторная очистка примерно через 30 секунд остаётся компенсацией гонки. Проверено чтением `gui.rs`, без управляемого Tauri-теста. Следующий технический шаг: поколение синхронизации, снимаемое вместе с настройками, и проверка поколения внутри короткой защищённой операции применения файлов, кешей и UI. Один check до сети не устраняет гонку; mutex на всю сеть задержит Forget.
- **F1, P1, reconnect:** Server расходует право старого Device до надёжного сохранения новых credentials. Потеря ответа или локальной записи остаётся невосстановимой. Существующий `TODO(audit)` сохранён. Семантика повторного reconnect затрагивает pairing и ADR 0045; её нужно согласовать с владельцем до изменения протокола.
- **F2, P1, свежесть:** `build_upload` объединяет Character и Account с одним `savedAt`, а `post_snapshots` подтверждает отправленные revisions по HTTP success. Существующий TODO сохранён. Нужен согласованный контракт свежести и результаты принятия Sections; простое разделение отправок может изменить обнаружение перемещений предметов и Wins.
- **F9/F4, P2, sync:** прежние Requests больше не прерывают пачку на временной ошибке, но отправка остаётся последовательной; их timeouts задерживают актуальный Plan. Временная ошибка ожидаемого Request всё ещё останавливает чтение готового Plan. Ошибки snapshot/profile/Suggestions/Advice по-прежнему отбрасываются. Нужны независимые результаты стадий и безопасная диагностика; правила уведомления игрока нельзя подменять техническим решением.
- **Остальные collectors:** исправлен только путь `achProgress`. В daily achievements, journal fallback и других сборщиках ещё есть прямые сравнения и обращения к API до полной санитарной проверки. Не заявляется безопасность всех secret values или исправление всего `Collections.lua`.
- **Другие HTTP-маршруты:** ограниченное чтение добавлено только для snapshot с уже принятым cap. Остальные JSON body limits, защита от медленной загрузки, proxy/server timeouts не проверены этим исправлением. Новых произвольных лимитов без спецификации не вводилось.
- Общий Prefetch budget после серии записей, межпроцессная координация, модель единственного владельца и зависимости не получили исправлений. Dependabot alert #5 остаётся открытым; обновление транзитивного GTK/glib требует отдельной проверки графа и целевых платформ.
